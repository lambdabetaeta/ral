# Release legal files

Original workspace code is MIT OR Apache-2.0. The modified Codex portions
identified in the root `NOTICE` remain Apache-2.0-only: the workspace's dual
licence does not offer an MIT alternative for them. `NOTICE` retains the
upstream Codex attribution, including its Ratatui attribution.

## Third-party notices

Every shipped binary carries a `THIRDPARTY-*` file reproducing the licences of
the third-party crates compiled into it: `THIRDPARTY-RAL`, `THIRDPARTY-EXARCH`,
`THIRDPARTY-SYNOD`, `THIRDPARTY-RAL-GUEST` (the guest's `/init`) and
`THIRDPARTY-OPENVMM`. cargo-about 0.9.3 generates them from the exact graph
that ships (package, target, features, and `Cargo.lock`) when the binary is
packaged; none is committed, so none can drift from what it describes.

- `packaging/about/about.toml` is the shared configuration: the accepted
  licences in priority order and per-crate clarifications, each pinning a
  licence text by checksum. `notices.hbs` renders the plain-text notice;
  `openvmm.hbs` adds the third-party code inside OpenVMM's own sources, which
  cargo-about cannot see.
- First-party crates are `publish = false`, which cargo-about treats as ours.
  Vendored third-party crates are not, and carry their upstream licence files.
- Generation fails on a licence not accepted, on a crate with no licence, and
  on a crate for which only cargo-about's SPDX reference text is found, as
  `Partial not found <crate>`. Clarify that crate in `about.toml`; only a crate
  that publishes no licence text anywhere belongs in `notices.hbs`'s list.
  `--format json` shows every crate whose `source_path` is null.
- `just third-party PACKAGE TARGET OUT [FEATURE...]` is the one invocation for
  this workspace, e.g. `just third-party ral x86_64-pc-windows-msvc
  target/THIRDPARTY-RAL allutils`. Install the generator with
  `cargo install --locked --features cli cargo-about@0.9.3`; CI uses the same
  version through `taiki-e/install-action`, and its `notices` job generates
  Synod's Windows notices on every pull request: that graph exercises the
  most clarifications.

## Binary delivery

- `scripts/package-release.sh BINARY ARCHIVE TARGET [FEATURE...]` packages Unix
  binaries as `.tar.gz` and Windows exarch as `.zip`. Every archive contains
  `LICENSE-APACHE`, `LICENSE-MIT`, `NOTICE`, and its generated `THIRDPARTY-RAL`
  or `THIRDPARTY-EXARCH`; exarch archives also contain `LICENSE-EDTUI`, copied
  verbatim from `vendor/edtui/LICENSE.md` (MIT, Copyright 2023 Philipp Reiter).
- Both the GitHub Actions matrix and `scripts/build-release.ral` use that
  packager. Checksums cover the archives. Do not publish the loose binaries.
- Unix download installers retain legal files in
  `${XDG_DATA_HOME:-$HOME/.local/share}/{ral,exarch}`. The Windows exarch
  installer retains them alongside `exarch.exe`.
- The ral MSI installs both licence texts, `NOTICE` and `THIRDPARTY-RAL`
  beside `ral.exe`; the `msi` job generates the notices for the Windows
  `allutils` payload. Winget installs that MSI and needs no separate legal-file
  payload.
- Source installs (`just install`, `scripts/install.ral`) retain legal files,
  with notices generated for the host, in `$CARGO_HOME/share/{ral,exarch}`.
- Homebrew HEAD builds install them, with notices generated for the host,
  in the formula's prefix; they need Homebrew's cargo-about at 0.9.3 and
  refuse to build otherwise.
- Synod bundles retain the four files and `THIRDPARTY-SYNOD`, generated by
  `just synod::bundle`, under their `licenses` resources. The Windows bundle
  installs `openvmm.exe` beside `synod.exe` and adds `LICENSE-OPENVMM`
  (upstream's MIT `LICENSE` at the pinned commit) and `THIRDPARTY-OPENVMM`;
  `scripts/build-openvmm.ps1` stages all three.
- The guest initramfs carries the four files, `THIRDPARTY-RAL-GUEST` and
  `THIRDPARTY-EXARCH` under `/usr/share/doc/exarch`; `vm-image/build-boot.sh`
  generates the notices for the guest target. Guest-root assembly copies these
  six files into the new root before `switch_root` reclaims the initramfs,
  and refuses to continue if a copy fails.

## Debian metadata

`ral/Cargo.toml` owns the only existing `package.metadata.deb` configuration.
Its `assets` include these entries (paths are relative to that crate):

```toml
{ source = "../LICENSE-APACHE", dest = "/usr/share/doc/ral/LICENSE-APACHE", mode = "644" },
{ source = "../LICENSE-MIT", dest = "/usr/share/doc/ral/LICENSE-MIT", mode = "644" },
{ source = "../NOTICE", dest = "/usr/share/doc/ral/NOTICE", mode = "644" },
{ source = "../target/third-party/THIRDPARTY-RAL", dest = "/usr/share/doc/ral/THIRDPARTY-RAL", mode = "644" },
```

Generate the last before `cargo deb`, for the target and features it builds,
e.g. `just third-party ral "$(rustc --print host-tuple)"
target/third-party/THIRDPARTY-RAL`.

Its `license-file` points to `../LICENSE-APACHE`; the installed licence texts
and `NOTICE` document the dual-licensed original code and Apache-only
adaptations. Exarch has no Debian package metadata. If one is added, include the same three files
under `/usr/share/doc/exarch/` plus `../vendor/edtui/LICENSE.md` installed there
as `LICENSE-EDTUI`, and its generated `THIRDPARTY-EXARCH`. Cargo package licence declarations must likewise not
claim an MIT alternative for the Codex-derived portions.
